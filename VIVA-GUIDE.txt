0.1  WHAT IS THIS PROJECT, IN ONE PARAGRAPH
-------------------------------------------
  It is a desktop application that pretends to be a stock-exchange surveillance
  terminal. It shows a live (simulated) market data feed, lets you place orders,
  watches that feed for suspicious trading behaviour, raises alerts, draws charts,
  produces audit reports, can replay historical data, and lets you configure it.
  It is ONE Java Swing application with ten modules, not ten programs. All the
  market data is SIMULATED - there is no real exchange connection.

0.2  THE 30-SECOND ANSWER IF THE FACULTY ASKS "EXPLAIN YOUR PROJECT"
--------------------------------------------------------------------
  "We built a single Java Swing desktop application with ten modules. Six of
   those modules are mine: Market Data, Alerts, Charting and Analytics, Audit
   Reports, Replay and Settings. The design has three layers - GUI panels,
   service classes, and model classes - and dependencies only point one way, so
   panels never contain business logic and services never touch Swing drawing.
   One javax.swing.Timer inside MarketDataService drives the whole application.
   Every panel subscribes to that feed through a listener interface, so all the
   screens always show the same, consistent data. No database, no external
   libraries - standard Java Swing only."

0.3  THE ARCHITECTURE DIAGRAM (draw this on the board if asked)
---------------------------------------------------------------
        gui/            panels: draw and react to clicks
          |
          v
        service/        logic: simulation, detection, maths, reports
          |
          v
        model/          plain data: fields and getters only
          |
          v
        util/           styling, demo data, formatting (knows nothing)

  RULE: dependencies point DOWN only. A panel may use a service. A service may
  use a model. A model never imports a panel. This is why the code is easy to
  explain: "panels draw, services decide, models carry."

0.5  WHY WE CHOSE EACH TECHNOLOGY (be ready for "why this and not that?")
-------------------------------------------------------------------------
  Q: Why Swing and not JavaFX or a web page?
  A: The project specification requires a Java Swing desktop front end and marks
     are awarded for Swing component usage. Swing is also part of standard Java,
     so there is nothing to install.

  Q: Why javax.swing.Timer and not Thread / SwingWorker / ExecutorService?
  A: This is the single most important technical decision. Timer fires its action
     on the Event Dispatch Thread (EDT), which is the only thread allowed to
     touch Swing components. Because the simulation runs on the EDT, every panel
     can update its labels and tables DIRECTLY from the listener. No locks, no
     thread-safe collections, no "GUI updated from wrong thread" bugs. With a
     background Thread we would have needed SwingUtilities.invokeLater everywhere
     and we would have risked random crashes.

  Q: Why is there no database?
  A: The first review only needs a working front end. All data is simulated in
     memory and recreated at start-up, which also means the examiner can restart
     the app and get a clean, predictable demo every time.

  Q: Why are the charts hand-drawn instead of using JFreeChart?
  A: The specification says a simple custom Swing visualisation is enough and to
     avoid installing complex chart libraries. Drawing with Graphics2D keeps the
     project dependency-free and it is a strong thing to demonstrate.

  Q: Why is the data simulated rather than read from a real ITCH file?
  A: Reading and decoding NASDAQ ITCH binary files is a backend task for a later
     review. For this review the interface and the behaviour had to be right, so
     the Replay module drives a simulated event stream behind the real controls.

  Q: Why one shared service instance instead of one per panel?
  A: If every panel created its own MarketDataService, the Market Data screen and
     the Alerts screen would show DIFFERENT prices. The main frame creates the
     services ONCE and injects them into every panel, so there is a single source
     of truth.

0.6  THE FIVE VOCABULARY WORDS THAT MAKE YOU SOUND LIKE YOU KNOW IT
------------------------------------------------------------------
  1. LAYERED ARCHITECTURE   - gui/service/model/util, one-way dependencies.
  2. EVENT DISPATCH THREAD  - the single thread that runs all Swing code.
  3. LISTENER / OBSERVER    - an object registers itself to be told when
                              something happens; the timer notifies subscribers.
  4. DEPENDENCY INJECTION   - passing a ready-made service into a panel's
     (constructor injection)  constructor instead of the panel creating it.
  5. SEPARATION OF CONCERNS - a class should have one job; an Alert does not
                              know how to draw itself, a panel does not know how
                              to compute a risk score.

PURPOSE
  The single place where every colour, font and shared widget style is defined.
  It is a utility class (all static, cannot be instantiated) plus a factory for
  pre-styled Swing components.

THE MOST IMPORTANT IDEA
  NO panel hard-codes a colour. If you want to change the whole application's
  look, you change it here once. This is what makes six different screens look
  like ONE product instead of six student programs. This is the first thing to
  say if asked about design.

SNIPPET 1 - the colour palette
------------------------------
    public static final Color BG          = new Color(0x0E1117);
    public static final Color SURFACE     = new Color(0x161B22);
    public static final Color SURFACE_ALT = new Color(0x1C2230);
    public static final Color BORDER      = new Color(0x2A3441);
    public static final Color TEXT        = new Color(0xE6EDF3);
    public static final Color TEXT_MUTED  = new Color(0x8B949E);
    public static final Color ACCENT      = new Color(0x1F6FEB);

    public static final Color GREEN       = new Color(0x3FB950);
    public static final Color RED         = new Color(0xF85149);
    public static final Color AMBER       = new Color(0xD29922);
    public static final Color PURPLE      = new Color(0xBC8CFF);

  EXPLANATION: dark greys for backgrounds, near-white for text, and four semantic
  colours. GREEN/RED are used for up/down and success/failure, AMBER for warning,
  PURPLE for medium severity. Using `static final` means the value is created once
  and can never be changed by accident.

  WHY: hard-coding `new Color(0x3FB950)` in six panels would mean six places to

  by MEANING (GREEN, RED, AMBER) also makes the panel code read like English.

  VIVA TIP: `0x0E1117` is hexadecimal - two hex digits each for red, green, blue.
  `0x0E`=14, `0x11`=17, `0x17`=23, so it is a very dark grey, not pure black.
  Pure black looks harsh; a slightly blue-grey reads as a professional terminal.

SNIPPET 2 - install(): the global look and feel
-----------------------------------------------
    public static void install() {
        try {
            UIManager.setLookAndFeel(UIManager.getCrossPlatformLookAndFeelClassName());
        } catch (Exception ignored) {
        }
        UIManager.put("Panel.background", SURFACE);
        UIManager.put("Table.background", SURFACE);
        UIManager.put("Table.foreground", TEXT);
        UIManager.put("Table.gridColor", BORDER);
        ...
    }

  EXPLANATION: `UIManager` holds the defaults for every Swing component.
  `setLookAndFeel` chooses the visual style; `UIManager.put("key", value)`
  overrides individual defaults globally.

  WHY the cross-platform look and feel: on macOS the default Aqua look and feel
  IGNORES many custom colours, so buttons and tables would come out light grey
  and the dark theme would look broken and inconsistent between our laptops and
  the lab machines. The cross-platform (Metal) look and feel obeys the colours
  on every operating system, so the screenshots look the same everywhere.

  WHY the try/catch with an empty body: setting the look and feel can throw, and
  if it fails we still want the application to start with the default look rather
  than crash. `ignored` is the conventional name for a deliberately ignored error.

  VIVA TIP: `install()` must be called BEFORE any Swing component is created -
  it is the very first thing the main method does. If you ask for it after, the
  components already built keep the old defaults.

SNIPPET 3 - the empty private constructor
-----------------------------------------
    public final class DarkTheme {
        ...
        private DarkTheme() {
        }
    }

  EXPLANATION: a class that is only a holder of static methods should never be
  instantiated. Making the constructor private prevents `new DarkTheme()` and
  `final` prevents subclassing. This is the standard Java "utility class" idiom.

SNIPPET 4 - the component factories
-----------------------------------
    public static JTextField field(int columns) {

    }

    public static JSpinner spinner(int min, int max, int step, int value) {
        JSpinner s = new JSpinner(new SpinnerNumberModel(value, min, max, step));
        s.setFont(FONT_BASE);
        s.setPreferredSize(new Dimension(90, FIELD_HEIGHT));
        ...

  EXPLANATION: instead of writing the same six lines of styling every time we

  we do not need to validate it later.

SNIPPET 5 - searchField() and readField(): the bug that taught us the most
------------------------------------------------------------------------
    public static JTextField searchField(String placeholder, int columns) {
        JTextField f = field(columns);
        f.putClientProperty("dsh.placeholder", placeholder);
        return f;
    }

    public static String readField(JTextField field) {
        if (field == null) {
            return "";
        }
        String text = field.getText();
        if (text == null) {
            return "";
        }
        Object placeholder = field.getClientProperty("dsh.placeholder");
        if (placeholder != null && text.equals(placeholder.toString())) {
            return "";
        }
        return text;
    }

  EXPLANATION: a "placeholder" is the grey hint text such as "Search symbol...".
  Swing's JTextField has NO built-in placeholder, so we store the hint in a
  client property instead of in the field's text. `readField` returns "" while
  the hint is still showing, and the real text once the user types.

  WHY - THIS IS A GREAT STORY TO TELL: our first version put the hint text into
  the field with the normal constructor, so the field's real text was literally
  "Search symbol or company...". The Market Data table filters rows by what is
  typed in that box, so the filter searched for the words "search symbol or
  company" and matched ZERO symbols - every table looked empty. `getClientProperty`
  / `putClientProperty` let us attach our own data to any Swing component without
  subclassing it, which is exactly what it is designed for.

  VIVA TIP: the lesson is "a hint is not data". Never store UI decoration in the
  same place as user input.

SNIPPET 6 - split(): the second bug, and why this method exists
--------------------------------------------------------------
    public static JSplitPane split(Component left, Component right, int leftWidth) {
        JSplitPane split = new JSplitPane(JSplitPane.HORIZONTAL_SPLIT, left, right);
        split.setBorder(BorderFactory.createEmptyBorder());
        split.setBackground(BG);
        split.setDividerSize(8);
        split.setContinuousLayout(true);
        split.setOneTouchExpandable(false);

        split.setResizeWeight(0.0);
        split.setDividerLocation(leftWidth);

        left.setMinimumSize(new Dimension(Math.min(leftWidth, 120), 100));
        right.setMinimumSize(new Dimension(320, 100));
        ...
        return split;
    }

  EXPLANATION: a JSplitPane shows two components with a draggable divider.
  `setDividerLocation(230)` says "put the divider 230 pixels from the left".
  `setMinimumSize` caps how small each side may be squeezed. `setResizeWeight(0)`
  means "when the window grows, give all the extra space to the RIGHT side".

  WHY - THE STORY: on the Settings screen the category tree on the left was
  squashed to about 20 pixels. We measured it and found the divider location was
  -1 (never set) and that the right-hand preferences form demanded a MINIMUM
  width of 1528 pixels inside a 1448 pixel pane. Swing resolved the conflict by
  giving the left side its minimum of 64 pixels. Fixing it in ONE shared method
  fixed all three split screens at once (Alerts, Audit Reports, Settings).

  VIVA TIP: if asked "why is this a shared method and not repeated?", the answer
  is "because we found the same bug in three places and did not want a fourth".

    public static void alignRight(JTable table, int columnIndex) {
        DefaultTableCellRenderer r = new DefaultTableCellRenderer();
        r.setHorizontalAlignment(SwingConstants.RIGHT);
        r.setFont(FONT_MONO);
        table.getColumnModel().getColumn(columnIndex).setCellRenderer(r);

  per column, not one per row.

FILE 3: src/util/DateTimeUtil.java 45 lines
--------------------------------------------------------------------------------
PURPOSE
  One place for every date/time format in the application, so all screens print
  timestamps identically.

SNIPPET
-------
    public static String time(long millis) {
        return new SimpleDateFormat("HH:mm:ss").format(new Date(millis));
    }

    public static boolean isValidDate(String text) {
        return text != null && parseDate(text) > 0;
    }

    public static long parseDate(String text) {
        try {
            SimpleDateFormat sdf = new SimpleDateFormat("yyyy-MM-dd");
            sdf.setLenient(false);
            return sdf.parse(text.trim()).getTime();
        } catch (Exception e) {
            return -1L;
        }
    }

  EXPLANATION: the method takes milliseconds since 1 January 1970 (an epoch
  timestamp, which is how Java stores time) and formats it as text.
  Format letters: HH = 24-hour, mm = minutes, ss = seconds, yyyy = year,
  MM = month, dd = day.

  WHY A NEW SimpleDateFormat EVERY CALL: SimpleDateFormat is NOT thread-safe.
  Sharing one static instance between threads causes wrong or corrupted output.
  Creating a small object is cheap; a heisenbug is not.

  WHY `setLenient(false)`: by default SimpleDateFormat "helpfully" accepts
  nonsense like 2024-02-31 and rolls it over to 2 March. With lenient false it
  throws, so validation actually works.

  VIVA TIP: `HH` vs `hh` - HH is 00-23 (24-hour), hh is 01-12 (12-hour). Getting
  this wrong makes an evening timestamp show as morning. Note the market
  timestamps in our screenshots are 23:11, which only looks right because we used
  capital HH.

THE ONE RULE FOR THIS WHOLE LAYER
  A model class holds DATA and provides GETTERS and SETTERS. It does not know
  about Swing, it does not know about services, it never prints anything. If you
  can say "this class is just a container for these fields", you are right.

  WHY WE DID THIS: if an Alert could also draw itself and calculate its own risk
  score, then changing the colour scheme would mean editing the Alert class, and
  changing the risk formula would mean editing the GUI. Splitting them means one
  reason to change each file.

    public class MarketRow {

        }

  EXPLANATION: `symbol` and `company` are `final` because an instrument's code
  and name never change during a session - once set in the constructor they can
  never be reassigned. Everything else is mutable because the simulation updates
  it on every tick.

SNIPPET - a calculated value
----------------------------
    public double getSpread() {
        return ask - bid;
    }

    public double getChangePercent() {
        double open = price - change;
        if (open == 0) {
            return 0;
        }
        return change / open * 100.0;
    }

    public String getChangeText() {
        return String.format("%+.2f", change);
    }

  EXPLANATION: `spread` is the gap between the best sell price (ask) and the best
  buy price (bid), and it is not stored - it is DERIVED from two fields we already
  have. Storing it would mean keeping three values consistent instead of two.

  `changePercent` divides by the opening price. The `if (open == 0)` guard
  prevents a division by zero, which for a double would produce `Infinity` and
  print as a nonsense number.

  `String.format("%+.2f", change)` - the `%+` forces a PLUS SIGN for positive
  numbers, and `.2f` means two decimal places. That is why the table shows
  "+0.12" and "-0.07" - the sign is part of the format, not something we add
  manually with an if statement.

  VIVA TIP: `%.2f` = 2 decimals, `%,d` = thousands separators (7,679,074),
  `%+.2f` = always show the sign. If asked how the numbers are formatted, this is
  the answer.

  WHY `toString()` returns the symbol: it makes the object print sensibly in a
  debugger or a combo box.

SNIPPET - getSeverity(): turning a number into a category
---------------------------------------------------------
    public String getSeverity() {
        if (riskScore >= 85) {
            return "CRITICAL";
        } else if (riskScore >= 65) {
            return "HIGH";
        } else if (riskScore >= 40) {
            return "MEDIUM";
        }
        return "LOW";
    }

  EXPLANATION: the risk score is 0-100 and is stored as a number, but a human
  reading a wall of alerts needs a category. This method maps number to band.

  WHY THIS IS A MODEL METHOD AND NOT A PANEL METHOD: every screen needs the same
  bands - the Alerts panel colours rows by it, Settings filters by it, the
  severity chart counts by it. Putting the rule in one place means they can never
  disagree. (This is the "single source of truth" principle again.)

  NOTE the order: the comparisons go from highest to lowest and the final return
  has no `if` because anything below 40 is LOW. This is a standard guard-chain.

PART E - the tick: what happens every second
--------------------------------------------
    private void tick() {
        tickCount++;

        for (MarketRow row : rows.values()) {
            movePrice(row);
            updateQuote(row);
            addVolume(row);
        }

        matchWorkingOrders();
        cancelStaleOrders();

        List<MarketRow> snapshot = getRows();
        for (MarketListener listener : listeners) {
            listener.onMarketUpdate(snapshot);
        }
    }

  EXPLANATION, STEP BY STEP (memorise these six steps):
    1. count the tick
    2. for every instrument: move the price, refresh bid/ask, add some volume
    3. try to execute any waiting orders
    4. occasionally cancel an order that has been sitting too long
    5. take a snapshot of the market
    6. tell every listener about it

  WHY A SNAPSHOT AND NOT THE LIVE MAP: we pass a read-only copy so a listener
  cannot accidentally modify the market while other listeners are reading it.
  `getRows()` returns `Collections.unmodifiableList(new ArrayList<>(rows.values()))`
  - a copy that throws if anyone tries to change it.

PART F - movePrice(): the random walk
-------------------------------------
    private void movePrice(MarketRow row) {
        double price = row.getPrice();
        double open = getOpenPrice(row.getSymbol());

        double drift = (open - price) / open * 0.05;
        double noise = (random.nextDouble() - 0.5) * 2 * MAX_TICK_MOVE_PERCENT / 100.0;
        double factor = 1.0 + drift + noise;

        double newPrice = round2(Math.max(0.01, price * factor));
        row.setPrice(newPrice);
        row.setChange(round2(newPrice - open));
        row.setTimestamp(System.currentTimeMillis());
    }

  EXPLANATION:
  - `drift` pulls the price back towards the session's opening price. If the price
    is ABOVE the open, `(open - price)` is negative, so the drift is negative and
    pushes the price down. This is MEAN REVERSION.
  - `noise` is a small random nudge: `random.nextDouble()` gives 0.0 to 1.0, we
    subtract 0.5 to centre it on zero, so it can push either way.
  - `factor` is the multiplier applied to the price.
  - `Math.max(0.01, ...)` stops the price ever reaching zero or going negative.
  - `round2` keeps two decimal places, because a share price with 15 decimals
    looks wrong on screen.

  WHY NOT PURE RANDOM: with pure random noise the price wanders away and after a
  few minutes AAPL could be at 900 or at 3, which looks absurd in a demo. The
  gentle pull towards the open keeps everything realistic.

  VIVA TIP: this is a "mean-reverting random walk". Saying that phrase correctly
  is worth a lot.

PART G - matchWorkingOrders(): a tiny matching engine
-----------------------------------------------------
    private void matchWorkingOrders() {
        boolean changed = false;

        for (LiveOrder order : orders) {
            if (!order.isWorking()) {
                continue;
            }
            MarketRow row = rows.get(order.getSymbol());
            if (row == null) {
                continue;
            }

            boolean marketReached = order.isBuy()
                    ? order.getPrice() >= row.getAsk()
                    : order.getPrice() <= row.getBid();

            if (!marketReached) {
                continue;
            }

            int remaining = order.getRemainingQuantity();
            int fill = Math.max(1, Math.min(remaining, 50 + random.nextInt(450)));
            order.setFilledQuantity(order.getFilledQuantity() + fill);
            order.setLastUpdate(System.currentTimeMillis());
            order.setStatus(order.getRemainingQuantity() <= 0
                    ? LiveOrder.STATUS_FILLED
                    : LiveOrder.STATUS_PARTIAL);
            changed = true;
        }

        if (changed) {
            fireOrderChanged();
        }
    }

  EXPLANATION:
  - A BUY limit order can execute when its price is at or ABOVE the current ask
    (you are willing to pay at least what sellers want).
  - A SELL limit order can execute when its price is at or BELOW the current bid.
  - Orders fill in PIECES, not all at once: `Math.min(remaining, 50 + random...)`
    fills a random slice between 50 and 499 shares but never more than what is
    left. Real markets work this way.
  - The ternary sets FILLED if nothing remains, otherwise PARTIAL.
  - `changed` tracks whether anything happened, so we only notify listeners when
    there is actually news. This avoids pointless repaints.

  VIVA TIP: `Math.min` here is the important guard - without it an order for 500
  shares could be filled by 2000, producing negative remaining quantity and a
  nonsense "FILLED" order that is still owed shares.

  WHY THIS MATTERS FOR THE DEMO: Developer A's Order Book module calls
  `placeOrder(...)`, and the order then genuinely executes or gets cancelled over
  the following ticks. The "Executed" and "Cancelled" statistics in Analytics are
  therefore counting real events, not constants.

        AuditReport report = new AuditReport(store.nextReportId(), reportType,
                now, AuditReport.STATUS_READY, alertCount,
                periodLabel == null || periodLabel.trim().isEmpty()
                        ? DateTimeUtil.date(now) : periodLabel.trim(),
                80 + random.nextInt(900));

        store.addReport(report);
        return report;
    }

    public List<AuditReport> getReports() {
        return new ArrayList<>(store.getReports());
    }

    public boolean deleteReport(AuditReport report) {
        return report != null && store.getReports().remove(report);
    }

  EXPLANATION: `getReports()` returns a COPY of the list (note `new
  ArrayList<>(...)`), so a caller cannot modify the store's list by accident.
  `deleteReport` is the ONLY way to remove a report, and it deletes from the
  store.

  WHY THIS IS A REAL BUG WE FIXED AND A GREAT STORY: the Audit panel originally
  did `reportService.getReports().remove(report)`. That removed the report from a
  throw-away COPY, so the row vanished from the table and then reappeared as soon
  as the table refreshed - the store had never changed. We fixed it by adding
  `deleteReport` to the service. The lesson: never hand out your internal
  collection and expect callers to respect it; provide an explicit method.

  EXPORT IS SIMULATED ON PURPOSE: `exportReport` returns a message describing what
  WOULD happen. Writing a real CSV or PDF needs a library or a lot of code that
  earns nothing at this review. Only this one method would change later.

  explain any of them quickly:

    public class XxxPanel extends JPanel {
        private final SomeService service;          // injected, never created here

        // 1. declared as fields so listeners can reach them
        private final JTable table = new JTable(tableModel);
        private final JLabel statusLabel = ...;

        public XxxPanel(SomeService service) {
            this.service = service;
            setLayout(new BorderLayout(0, 10));
            setBackground(DarkTheme.BG);
            setBorder(BorderFactory.createEmptyBorder(14, 16, 14, 16));

            add(DarkTheme.header("Title", "subtitle"), BorderLayout.NORTH);
            add(buildCenter(), BorderLayout.CENTER);
            add(buildStatusBar(), BorderLayout.SOUTH);

            wireEvents();        // 2. attach all listeners
            refreshTable();      // 3. fill the table once
        }

        private void wireEvents() { ... }    // buttons, tables, filters
        private void refreshTable() { ... }  // rebuild from service data
        public void onMarketUpdate(...) { ... } // optional: live updates
    }

  WHY BorderLayout: NORTH holds the header, CENTER holds the main content and
  grows, SOUTH holds the status bar. The CENTER component automatically gets all
  the leftover space, which is exactly what we want for a table.

  the constructor cannot be reached from `wireEvents()` or `refreshTable()`. The
  components must be fields so the whole class can see them.

  WHY SERVICE INJECTION (constructor parameter): the panel receives a ready-made
  service. It does not create one. That is what allows the whole application to
  share a single source of truth, and it also makes the panel testable on its own.

  VIVA TIP: if asked "what is the entry point of a panel?", the answer is the
  constructor, and it does exactly three things: build the layout, wire the
  events, populate the data.

    private List<MarketRow> applyFilter(List<MarketRow> source) {
        String query = DarkTheme.readField(searchField).trim().toLowerCase();
        String view = (String) viewBox.getSelectedItem();

        List<MarketRow> result = new ArrayList<>();
        for (MarketRow row : source) {
            if (!query.isEmpty()) {
                boolean matchesSymbol = row.getSymbol().toLowerCase().contains(query);
                boolean matchesCompany = row.getCompany().toLowerCase().contains(query);
                if (!matchesSymbol && !matchesCompany) {
                    continue;
                }
            }
            if ("Watchlist only".equals(view) && !watchlistModel.contains(row.getSymbol())) {
                continue;
            }
            result.add(row);
        }

        if ("Top gainers".equals(view) || "Top losers".equals(view)) {
            result.sort((a, b) -> "Top gainers".equals(view)
                    ? Double.compare(b.getChange(), a.getChange())
                    : Double.compare(a.getChange(), b.getChange()));
            if (result.size() > 10) {
                result = new ArrayList<>(result.subList(0, 10));
            }
        }
        return result;
    }

  EXPLANATION: it builds a NEW list containing only the rows that pass every
  check. `toLowerCase()` on both sides makes the search case-insensitive.
  `contains(query)` means the search matches anywhere in the text, so "nv" finds
  NVDA.

  The sorting uses a LAMBDA COMPARATOR: `(a, b) -> Double.compare(...)`.
  For "Top gainers" it compares `b` to `a` (descending); for "Top losers" it
  compares `a` to `b` (ascending). `Double.compare` is the correct way to compare
  doubles - subtracting them is unsafe with floating point.

  `subList(0, 10)` takes the first ten.

  WHY THIS IS ITS OWN METHOD: it is pure logic with no Swing calls, so it is easy
  to test, and `refreshTable` stays short.

    private class RiskRenderer extends DefaultTableCellRenderer {
        RiskRenderer() {
            setHorizontalAlignment(SwingConstants.CENTER);
            setFont(DarkTheme.FONT_BOLD);
        }

        @Override
        public Component getTableCellRendererComponent(JTable t, Object value,
                boolean isSelected, boolean hasFocus, int row, int column) {
            Component c = super.getTableCellRendererComponent(
                    t, value, isSelected, hasFocus, row, column);
            if (!isSelected) {
                int risk = 0;
                try {
                    risk = Integer.parseInt(String.valueOf(value));
                } catch (NumberFormatException ignored) {
                }
                Color color;
                if (risk >= 85) {
                    color = DarkTheme.RED;
                } else if (risk >= 65) {
                    color = DarkTheme.AMBER;
                } else if (risk >= 40) {
                    color = DarkTheme.PURPLE;
                } else {
                    color = DarkTheme.GREEN;
                }
                c.setForeground(color);
                c.setBackground(row % 2 == 0 ? DarkTheme.SURFACE : DarkTheme.SURFACE_ALT);
            }
            return c;
        }
    }

  EXPLANATION: a cell renderer is a "rubber stamp" the JTable reuses to paint
  cells. We subclass DefaultTableCellRenderer and, in `getTableCellRendererComponent`,
  decide the colour for this cell before returning it.

  - `super.getTableCellRendererComponent(...)` first does the normal work (setting
    the text), then we adjust the colour.
  - `if (!isSelected)` - when a row is selected the theme's selection colour must
    win, otherwise the highlight would be invisible.
  - `row % 2 == 0` alternates the background - this is where the striping comes

  to see danger instantly. Colour communicates severity pre-attentively, before
  the number is even read.

  VIVA TIP: `%` is the remainder operator. `10 % 5 == 0`, `11 % 5 == 1`. Checking

        protected void paintComponent(Graphics g) {
            super.paintComponent(g);

            g2.setRenderingHint(RenderingHints.KEY_ANTIALIASING,
                    RenderingHints.VALUE_ANTIALIAS_ON);

            int left = 58;
            int right = getWidth() - 14;
            int top = 12;
            int bottom = getHeight() - 26;
            int width = right - left;
            int height = bottom - top;
            ...
            double min = Double.MAX_VALUE;
            double max = -Double.MAX_VALUE;
            for (PricePoint point : series) {
                min = Math.min(min, point.getPrice());
                max = Math.max(max, point.getPrice());
            }
            double padding = Math.max((max - min) * 0.1, 0.05);
            min -= padding;
            max += padding;
            double range = max - min;

            int[] xs = new int[series.size()];
            int[] ys = new int[series.size()];
            for (int i = 0; i < series.size(); i++) {
                xs[i] = left + (int) Math.round((double) width * i / (series.size() - 1));
                double value = series.get(i).getPrice();
                ys[i] = top + (int) Math.round(height * (max - value) / range);
            }

            boolean rising = series.get(series.size() - 1).getPrice()
                             >= series.get(0).getPrice();
            Color lineColor = rising ? DarkTheme.GREEN : DarkTheme.RED;

            g2.setColor(lineColor);
            g2.setStroke(new BasicStroke(2f, BasicStroke.CAP_ROUND, BasicStroke.JOIN_ROUND));
            g2.drawPolyline(xs, ys, xs.length);
        }
    }

  EXPLANATION - THIS IS THE MOST IMPRESSIVE THING TO BE ABLE TO EXPLAIN:
  - `left/right/top/bottom` define a drawing area, leaving a 58-pixel gutter on
    the left for the price labels and 26 pixels at the bottom for the time labels.
  - We scan the series to find `min` and `max` so the chart auto-scales to the
    data. `Double.MAX_VALUE` and `-Double.MAX_VALUE` are the standard way to start
    a min/max search.
  - `padding` adds 10% headroom so the line does not touch the top or bottom edge.
    `Math.max(..., 0.05)` handles the case where every price is identical, which
    would otherwise make `range` zero and cause a division by zero.
  - THE COORDINATE CONVERSION IS THE KEY IDEA: `xs[i]` maps point i evenly across
    the width, and `ys[i]` flips the value. Note `(max - value)` - screen Y grows
    DOWNWARD, so a higher price must produce a SMALLER y. That inversion is why
    the chart is not upside down.
  - `drawPolyline(xs, ys, length)` draws the whole line in one call.
  - The line is GREEN if the last price is at or above the first, RED otherwise -
    so the colour comes from the data.

  VIVA TIP: if asked "how does the chart work without a library?", the answer is:
  "I find the min and max, scale each value into pixel coordinates, and call
  drawPolyline. The only subtlety is that screen Y is inverted compared to price."

  ALSO IN THIS CLASS: hover tracking for the crosshair and tooltip -
  `mouseMoved` sets `hoverIndex` via `indexAt(e.getX())` and calls `repaint()`;
  `mouseExited` resets it to -1.

  ALSO IN THIS CLASS: a moving average drawn in PURPLE. For each point it averages
  the previous `smoothing` values:
      for (int j = Math.max(0, i - smoothing + 1); j <= i; j++) { sum += ...; }
  `Math.max(0, ...)` stops the window running off the start of the list.

SNIPPET 3 - the simulated market clock
--------------------------------------
    private String simulatedTime() {
        long startOfSession = 9 * 3600_000L + 30 * 60_000L;
        long millis = startOfSession + simulatedClock;
        long hours = millis / 3600_000L % 24;
        long minutes = millis / 60_000L % 60;
        long seconds = millis / 1000L % 60;
        return String.format("%02d:%02d:%02d", hours, minutes, seconds);
    }

  EXPLANATION: the session starts at 09:30 (the real US market open). We build
  that as milliseconds: 9 hours x 3600000 + 30 minutes x 60000. Then we add the
  simulated elapsed time and convert the total back into hours, minutes and
  seconds.

  - `millis / 3600_000L` gives total hours; `% 24` wraps it into a 24-hour clock.
  - `millis / 60_000L % 60` gives minutes within the hour.
  - `%02d` pads with a leading zero so you see "09:30:05" and not "9:30:5".

  WHY INTEGER ARITHMETIC WORKS HERE: all the divisions are on longs, so the
  fractional part is discarded - which is exactly the truncation we want for
  "how many whole hours have passed".

6.2  THE THREE REAL BUGS WE FOUND AND FIXED (excellent things to volunteer)
--------------------------------------------------------------------------
  BUG 1 - EVERY TABLE WAS EMPTY
    Cause : the search fields were constructed with their placeholder text as
            real text, so the table filter searched for the words
            "Search symbol or company" and matched nothing.
    Fix   : the placeholder is stored in a client property, and all reads go
            through DarkTheme.readField().
    Lesson: a hint is not data. Never store UI decoration where user input goes.

  BUG 2 - THE SETTINGS TREE WAS 20 PIXELS WIDE
    Cause : the preferences form demanded a minimum width of 1528 pixels inside
            a 1448-pixel pane, and the divider location had never been set (-1),
            so Swing squeezed the left panel to its 64-pixel minimum.
    Fix   : one shared DarkTheme.split(...) method that sets the divider location
            and caps the right-hand minimum size.
    Lesson: set the divider location explicitly, and always cap minimum sizes.

  BUG 3 - THE ALERTS FILTER BAR CLIPPED ITS OWN CONTROLS
    Cause : one long FlowLayout line asked for more width than the pane had, and
            Swing clipped the last controls (Search and Reset) off the edge.
    Fix   : a GridLayout row, which divides the available width instead of
            demanding a total.
    Lesson: FlowLayout is for small rows; use a grid when the row must fit.

  BUG 4 - DELETED REPORTS CAME BACK
    Cause : the panel did reportService.getReports().remove(report), which removed
            the item from a returned COPY, so the store never changed.
    Fix   : ReportService.deleteReport(report) deletes from the store.
    Lesson: never hand out your internal collection; provide an explicit method.

  HOW WE FOUND THEM: not by reading code. By RUNNING it and RENDERING it. The
  screenshot tools made the bugs obvious in seconds.

6.3  LIKELY VIVA QUESTIONS WITH MODEL ANSWERS
---------------------------------------------
  Q: Which design pattern have you used?
  A: The Observer pattern - MarketDataService defines a MarketListener interface
     and notifies all registered listeners on every tick. SurveillanceService and
     AnalyticsService also use it. We deliberately kept it as a small custom
     interface instead of a complex framework.

  Q: Why is all your simulation in the service layer and not in the panels?
  A: Separation of concerns. A panel should only build components and react to
     events. If the price simulation lived in MarketDataPanel, the Order Book and
     Dashboard could not reuse it and we would have duplicated the logic.

  Q: What happens exactly when one market tick occurs?
  A: The Timer fires on the EDT and calls tick(). tick() moves each price, updates
     the quotes and volumes, matches any waiting orders, cancels stale ones, takes
     a read-only snapshot, then calls onMarketUpdate on every listener. The Market
     Data panel rebuilds its table, SurveillanceService may raise an alert, and
     AnalyticsService appends to its price history. All of that happens on one
     thread, in order, before the next tick.

  Q: Why not use a Thread for the simulation?
  A: Swing is not thread-safe. Only the Event Dispatch Thread may touch components.
     javax.swing.Timer fires on the EDT, so no synchronisation or invokeLater is
     needed anywhere and there is no risk of random GUI corruption.

  Q: How would you add persistence?
  A: Only DataStore and SettingsStore need changing. The panels already talk to
     those classes rather than to files, so no GUI code would change.

  Q: How would you make the rules actually work in the next review?
  A: SurveillanceService.createAlert is the single insertion point. A real rule
     engine would evaluate conditions against the market snapshot there and call
     createAlert only when a rule matched. The GUI would not change.

  Q: Why is there a "no-argument" constructor on some panels?
  A: So a panel can create its own services and be run and tested by itself.
     The main application always uses the constructor that takes injected
     services, so all panels share one source of truth.

  Q: What is the difference between JCheckBox and JRadioButton?
  A: Checkboxes are independent - any combination is valid. Radio buttons inside a
     ButtonGroup are mutually exclusive - exactly one. We used radio buttons for
     the theme and the replay mode because those genuinely are exclusive.

  Q: How do you stop the timers when the window closes?
  A: The frame uses DO_NOTHING_ON_CLOSE and a windowClosing listener that calls
     content.shutdown(), which stops the market timer, switches off monitoring and
     detaches the analytics listener. Only then does it dispose and exit.

  Q: Where is the risk score calculated?
  A: In SurveillanceService.onMarketUpdate - a random score between 25 and 94 for
     the demo. Alert.getSeverity() maps that number into the four severity bands,
     and that method lives in the model so every screen uses the same boundaries.

  Q: How does the search box work?
  A: The document listener fires on every keystroke, so refreshTable runs and
     applyFilter returns only the rows whose symbol or company contains the typed
     text, case-insensitively. It reads the field through
     DarkTheme.readField().

  Q: How are the charts drawn without a library?
  A: With Graphics2D in paintComponent. We find the minimum and maximum value in
     the series, map each value to a pixel coordinate, and draw with drawPolyline
     or fillRoundRect. The only subtlety is that screen Y increases downwards, so
     the value must be inverted: y = top + height * (max - value) / range.

  Q: What is a cell renderer?
  A: A component that a JTable, JTree or JList reuses as a rubber stamp to paint
     cells. We subclass DefaultTableCellRenderer and change the colour inside
     getTableCellRendererComponent, which is how the risk column turns red for
     high scores and green for low ones.

  Q: Why is your code so long?
  A: Three reasons: six full screens each with their own layout, two custom charts
     plus two custom-painted components, and a viva-free codebase with no comments
     and deliberately explicit code rather than condensed clever code. We chose
     readability over brevity.

  Q: What would you do differently?
  A: Three things. We would use enums instead of String constants for the statuses.
     We would persist the settings with java.util.prefs. And we would put the shared
     style and table code into a common base panel class, because all six panels
     now repeat the same setup pattern.

6.4  THE 60-SECOND SUMMARY TO MEMORISE
--------------------------------------
  "Market Surveillance Engine is one Java Swing desktop application with ten
   modules; I built six of them. It is layered - panels, services, models, util -
   and dependencies point one way only, so panels never contain business logic.
   One javax.swing.Timer in MarketDataService drives the entire application, and
   panels and services subscribe to it through a small Observer-style listener
   interface, which is why every screen always shows consistent data. There is no
   database and no external library: it is standard Java Swing, including three
   charts I painted myself with Graphics2D. We verified it with a headless smoke
   test, a pre-submission checker and screenshot rendering, which found four real
   bugs that reading the code had missed."

    private int levelSize(String symbol, String side, int level) {

FILE 28: src/model/SurveillanceRule.java                   237 lines
--------------------------------------------------------------------------------
  A surveillance rule: an id, a name, a list of conditions, AND/OR logic, a
  severity, a detection type, an enabled flag and a match counter.

  THE NESTED CLASS - RuleCondition:

    public static class RuleCondition {
        private String field;
        private String operator;
        private double value;
        private double value2;
        ...
        public boolean isRange() {
            return "between".equals(operator);
        }
        public String getConditionText() {
            return field + " " + operator + " " + getValueText();
        }
    }

  WHY NESTED AND NOT A SEPARATE FILE: a condition has no meaning outside its
  rule. Nesting keeps the two concepts together and stops the model package
  filling with tiny classes. The fields are not final because the user can edit
  a condition after creating it.

  WHY THERE IS A SECOND VALUE: the "between" operator needs an upper bound. For
  every other operator value2 is simply ignored, and the panel disables that box
  so the user cannot be confused.

  THE PRETTY-PRINTED NUMBER:

    private static String trim(double number) {
        if (number == Math.floor(number) && !Double.isInfinite(number)) {
            return String.valueOf((long) number);
        }
        return String.format("%.2f", number);
    }

  WHY: conditions read far better as "Order Size > 5000" than "Order Size >
  5000.0". This prints whole numbers without a decimal point and keeps two
  decimals otherwise. Math.floor is used to test whether a value is whole.

  getSummary() joins the conditions with the chosen logic, producing text such as
  "Order Size > 5000 AND Order Lifetime (ms) < 500". This is what the Alerts and
  Dashboard screens would display as the rule that fired.

  VIVA TIP: if asked "does the rule actually run?", answer honestly: "this build
  stores and manages rules. Evaluation would plug into
  SurveillanceService.onMarketUpdate, where each rule would be tested against the
  market snapshot before an alert is raised."
